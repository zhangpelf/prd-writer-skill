# PRD 撰写技能

## 用途

在 Claude Code 会话中，通过结构化对话高效生成专业级产品需求文档（PRD）。无需额外付费 LLM API，直接利用当前 AI 助手的能力完成撰写。

## 触发方式

在 Claude Code 中输入以下任一方式触发：
- `/prd-writer`
- `帮我写一份 PRD`
- `撰写产品需求文档`
- `prd 模板`

## 使用流程

### 第一步：提供产品信息

向 Claude 提供以下信息（不需要一次性给全，可以分步对话）：

```
产品名称：[名称]
目标用户：[描述]
核心问题：[解决什么问题]
关键功能：[主要功能点]
约束条件：[时间、预算、技术栈等]
```

### 第二步：选择 PRD 深度

Claude 会根据信息完整度自动选择，你也可以主动指定：

- **精简版**（1-2 小时完成）：适合快速对齐、内部评审
  - 概述 + 核心功能 + 验收标准
  
- **标准版**（半天）：适合正式立项、跨团队沟通
  - 完整 6 个章节
  
- **深度版**（1-2 天）：适合复杂系统、外部交付
  - 完整 6 章 + 技术架构 + 测试策略 + 运维方案

### 第三步：分章节生成

建议按以下顺序逐个章节生成，每章完成后确认再继续：

1. **概述**（先写，作为全文基调）
2. **功能需求**（核心，耗时最长）
3. **非功能需求**（技术约束）
4. **数据模型/接口**（技术对接需要）
5. **发布计划**（项目管理需要）
6. **风险评估**（最后写，基于前面内容）

### 第四步：验收检查

生成完成后，使用下方「检查清单」逐项确认。

## PRD 标准模板

### 1. 概述

```markdown
## 1. 概述

### 1.1 产品背景
[产品产生的业务背景、市场机会、用户痛点]

### 1.2 目标用户
| 用户类型 | 特征 | 使用场景 | 核心诉求 |
|---------|------|---------|---------|
| [类型1] | [特征] | [场景] | [诉求] |

### 1.3 核心目标
- 业务目标：[可量化的业务指标]
- 用户目标：[解决用户的什么问题]
- 技术目标：[系统层面的目标]

### 1.4 成功指标（KPI）
| 指标 | 基线 | 目标 | 测量方式 | 时间范围 |
|------|------|------|---------|---------|
| [指标1] | [当前值] | [目标值] | [如何测量] | [时间] |
```

### 2. 功能需求

```markdown
## 2. 功能需求

### 2.1 用户故事
作为 [用户类型]，我希望 [目标]，以便 [价值]。

### 2.2 功能列表

#### P0 - 必须实现（MVP）
| 功能 | 用户故事 | 验收标准 | 优先级 | 预估工时 |
|------|---------|---------|--------|---------|
| [功能1] | [故事] | [标准] | P0 | [工时] |

#### P1 - 重要但不阻塞发布
| 功能 | 用户故事 | 验收标准 | 优先级 | 预估工时 |
|------|---------|---------|--------|---------|
| [功能1] | [故事] | [标准] | P1 | [工时] |

#### P2 - 未来迭代
| 功能 | 用户故事 | 验收标准 | 优先级 | 预估工时 |
|------|---------|---------|--------|---------|
| [功能1] | [故事] | [标准] | P2 | [工时] |

### 2.3 验收标准（Given/When/Then）
**功能：[功能名称]**

**场景 1：正常流程**
- Given [前置条件]
- When [用户操作]
- Then [预期结果]
- And [额外结果]

**场景 2：异常流程**
- Given [前置条件]
- When [异常操作]
- Then [错误处理]
```

### 3. 非功能需求

```markdown
## 3. 非功能需求

### 3.1 性能需求
| 指标 | 要求 | 测试方法 |
|------|------|---------|
| 响应时间 | < 200ms (P95) | 压力测试 |
| 并发用户 | 支持 10,000 | 负载测试 |
| 可用性 | 99.9% | 监控告警 |

### 3.2 安全需求
- 数据加密：[传输/存储要求]
- 访问控制：[权限模型]
- 合规要求：[GDPR/等保/其他]

### 3.3 兼容性
- 浏览器：[支持的浏览器版本]
- 移动端：[iOS/Android 版本]
- 降级策略：[当功能不可用时]

### 3.4 可扩展性
- 数据增长预期：[存储增长预测]
- 功能扩展：[预留的扩展点]
```

### 4. 数据模型与接口

```markdown
## 4. 数据模型与接口设计

### 4.1 核心实体
```
User {
  id: UUID
  name: String
  email: String
  role: Enum[admin, user, guest]
  createdAt: DateTime
}
```

### 4.2 API 定义
| 接口 | 方法 | 路径 | 请求体 | 响应 | 错误码 |
|------|------|------|--------|------|--------|
| [名称] | [GET/POST] | [/api/...] | [结构] | [结构] | [错误码] |
```

### 5. 发布计划

```markdown
## 5. 发布计划

### 5.1 里程碑
| 阶段 | 时间 | 交付物 | 负责人 | 依赖 |
|------|------|--------|--------|------|
| [阶段1] | [日期] | [交付物] | [人] | [依赖] |

### 5.2 版本规划
- v0.1：[MVP 范围]
- v0.2：[P1 功能]
- v1.0：[正式版]
```

### 6. 风险评估

```markdown
## 6. 风险评估

| 风险 | 类型 | 概率 | 影响 | 缓解措施 | 负责人 |
|------|------|------|------|---------|--------|
| [风险1] | [技术/业务] | [高/中/低] | [高/中/低] | [措施] | [人] |
```

## Prompt 技巧

### 让 Claude 生成更好 PRD 的技巧

1. **提供上下文**
   ```
   我们正在做一个 [产品类型]，面向 [用户群体]，
   主要解决 [核心问题]。技术栈是 [技术栈]。
   请帮我写一份标准版 PRD。
   ```

2. **要求结构化输出**
   ```
   请严格按照上方「功能需求」模板的格式输出，
   包含完整的 Given/When/Then 验收标准。
   ```

3. **迭代优化**
   ```
   这个功能的验收标准不够具体，请补充边界条件：
   - 空输入如何处理？
   - 最大长度限制？
   - 并发冲突如何处理？
   ```

4. **技术深度控制**
   ```
   技术实现部分请保持高Level，不需要具体代码，
   但关键接口和数据流需要明确。
   ```

5. **对比参照**
   ```
   类似产品 [竞品A] 和 [竞品B] 都有这个功能，
   请分析差异点并在 PRD 中体现我们的差异化设计。
   ```

## 检查清单

在 PRD 完成前，确认以下项目：

### 内容完整性
- [ ] 所有 P0 功能都有明确的用户故事
- [ ] 每个功能都有至少 2 个验收标准（正常 + 异常）
- [ ] 非功能需求包含性能、安全、兼容性
- [ ] 数据模型包含所有核心实体
- [ ] API 定义包含错误处理
- [ ] 发布计划有明确的里程碑和依赖关系
- [ ] 风险评估包含缓解措施和负责人

### 质量检查
- [ ] 没有模糊的描述（如"快速""友好"，改为具体数字）
- [ ] 技术术语使用一致
- [ ] 没有未定义的缩写
- [ ] 验收标准可测试（能用自动化测试或人工测试验证）
- [ ] 优先级划分合理（P0 不超过 3-5 个核心功能）

### 可读性
- [ ] 目录结构清晰
- [ ] 表格对齐、格式统一
- [ ] 关键决策有简短的「为什么」说明
- [ ] 附录包含术语表（如有必要）

## 进阶技巧

### 多人协作
- 使用 Claude 生成初稿后，导出为 Markdown
- 团队成员在 GitHub/Notion 上评论和修改
- 重大变更使用 Claude 重新生成对应章节

### 版本管理
- v0.1 → v0.2 的变更使用「变更日志」格式记录
- 每个版本标记修改日期和负责人

### 与其他文档衔接
- PRD → 技术设计文档：PRD 的「数据模型/接口」章节作为输入
- PRD → 测试计划：PRD 的「验收标准」直接转化为测试用例
- PRD → 用户手册：PRD 的「用户故事」转化为帮助文档

## 常见错误

❌ **功能列表变成技术实现细节**
✅ 正确：描述「用户能做什么」，不是「系统怎么实现」

❌ **验收标准不可测**
✅ 正确：每个标准都能回答「怎么验证这个功能完成了？」

❌ **所有功能都是 P0**
✅ 正确：严格区分必须实现和重要但不阻塞的功能

❌ **忽略异常流程**
✅ 正确：每个功能至少考虑网络错误、权限不足、数据为空 3 种异常

❌ **没有成功指标**
✅ 正确：每个目标都要有数字化的 KPI

## 示例对话

**用户**：帮我写一份 PRD，做一个智能投研 Agent 平台

**Claude**：好的，我来为你生成一份标准版 PRD。在开始之前，请补充以下信息：
1. 目标用户是谁？（个人投资者 / 机构投资者 / 分析师？）
2. 覆盖哪些市场？（A股 / 港股 / 美股？）
3. 核心功能优先级？（数据采集 / 分析 / 报告生成？）
4. 有什么技术约束？（需要本地化部署 / 云端 SaaS？）

请提供这些信息，或者如果你不确定，我可以先基于常见场景生成初稿，然后我们一起迭代优化。

**用户**：面向个人投资者，A股为主，核心功能：数据采集和报告生成，云端 SaaS

**Claude**：[开始按模板生成各章节...]

3. 导入 Notion / 飞书文档 / GitHub Wiki
